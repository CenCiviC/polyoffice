# 구글 문서 기능 인벤토리 — "최소한 이만큼은" 기준선

목표: **구글 문서(Google Docs)가 가진 편집 기능을 최소 기준선으로 삼는다.** 그러려면
먼저 그 목록이 있어야 한다. 이 문서는 구글 문서 데스크톱 메뉴를 전수로 훑어
Narro의 현재 상태와 나란히 놓은 것이다.

> **이 문서는 작업 *전에* 쓴 격차 분석이다.** v0.2에서 링크·첨자·문단 여백·페이지 설정이
> 들어가 아래 표의 일부가 낡았다 — 해당 행은 ✅로 갱신했다.
> **지금 남은 일과 순서는 [TODO.md](TODO.md)를 본다.**

상태 기호:

- ✅ — 편집기에서 되고, IR에 담기고, 최소 한 개 백엔드로 저장된다
- ◐ — 일부만 (읽기만 되거나, 편집은 되는데 저장에서 강등되거나, IR에 슬롯만 있음)
- ✗ — 없음
- ⊘ — **의도적으로 범위 밖** (클라우드·협업·AI. 이유는 마지막 절)

"IR 요구"는 이 기능을 넣으려면 [IR-SPEC.md](IR-SPEC.md)의 어휘·스타일 목록에
무엇을 추가해야 하는지다. 스펙 규칙 1에 따라 **hwpx·docx 매핑이 정의되기 전에는
어휘를 추가할 수 없으므로**, 그 매핑 후보도 함께 적었다.

## 3. 삽입

여기가 격차의 대부분이다.

| 기능 | Narro | IR 요구 / 메모 |
|---|:--:|---|
| 이미지 | ✅ | data URI, 인라인 앵커 고정 |
| — 자르기 · 재색상 · 밝기/대비 · 테두리 | ✗ | 잘라낸 결과를 캔버스로 구워 넣으면 IR 변경 없이 가능(원본 손실) |
| — 텍스트 줄바꿈(둘러싸기/뒤로/앞으로) · 위치 고정 | ✗ | IR에 `data-wrap`·`data-anchor` 필요. hwpx `textWrap`(이미 `TOP_AND_BOTTOM` 고정 출력 중), docx `wp:anchor` |
| — 대체 텍스트(alt) | ◐ | IR `img[alt]` 있음. 편집 UI 없음 |
| 표 삽입 | ✅ | 행/열 추가·삭제, 병합, 병합 해제 |
| — 셀 배경색 | ✅ | IR·백엔드·편집 UI(셀 서식 다이얼로그) 전부 |
| — 셀 테두리(선 두께·색·종류) | ✅ | IR `border` 축약. 세 포맷 모두 실물에서 확인한 종류·굵기로 나간다(`bun run cell-sim`) |
| — 셀 세로 정렬(위/중간/아래) | ✅ | IR `vertical-align` → hwpx `subList vertAlign` · docx `w:vAlign` · odt `style:vertical-align` |
| — 열 너비 · 행 높이 드래그 | ◐ | IR에 pt로 있음. 드래그 UI 없음 |
| — 행 균등 배분 · 정렬(sort) · 헤더 행 고정 | ✗ | 고정은 hwpx `repeatHeader`, docx `w:tblHeader` |
| — 셀 분할(split) | ✗ | 병합의 역이지만 격자 재계산이 필요 |
| — 표↔텍스트 변환 | ✗ | |
| 가로줄 | ✗ | `<hr>` 추가. hwpx는 문단 테두리 아래선, docx `w:pBdr bottom` |
| 각주 | ✅ | 읽기·쓰기·삽입 UI 전부. 번호는 저장하지 않는다(각 포맷의 각주 기능이 센다) |
| 미주 | ◐ | 읽을 땐 각주로 흡수. 별도 어휘 없음 |
| 머리글 / 바닥글 | ✅ | IR `doc-header`/`doc-footer`. 쓰기 세 포맷, hwpx 매핑은 실물 한글 문서에서 확정 |
| 페이지 번호 / 전체 페이지 수 | ◐ | 쪽번호는 세 포맷 다 된다(`doc-field data-kind="page"`). **전체 쪽수는 hwpx만 강등** — `numType` 값을 아직 못 봤다 |
| 페이지 나누기 | ✅ | `doc-pagebreak` |
| 구역 나누기(다음 페이지 / 연속) | ◐ | `doc-section`은 있으나 편집기에서 못 만듦. docx 다중 sectPr은 읽기도 미지원(README) |
| 열(단) 나누기 — 2단·3단 | ✗ | 큰 건. hwpx `hp:colPr`, docx `w:cols`, odt `style:columns` |
| 링크(하이퍼링크) | ✅ | 읽기 docx·odt·hwpx, 쓰기 **세 포맷 전부**. hwpx `Command` 문법은 한글이 저장한 골든에서 확정했다(`samples/hwpx/golden/`) |
| 책갈피 · 문서 내 링크 | ✗ | `data-id`가 이미 블록 주소라 앵커로 재사용 가능 |
| 목차(TOC) | ✗ | h1–h6 + `data-id`로 생성 가능. 파생물이라 IR 규칙 2상 "저장 안 함" 대상 — 필드로 넣을지 텍스트로 구울지 결정 필요 |
| 특수문자 팔레트 | ✗ | 순수 UI. IR 변경 없음 |
| 이모지 | ◐ | 입력은 됨(그냥 문자). 팔레트 없음 |
| 수식 | ✗ | IR `doc-eq[data-latex]` 슬롯 정의됨. hwpx는 한글 수식 스크립트 변환기 자작 필요 (매핑 신뢰도 ○) |
| 그림(도형·선·화살표·텍스트박스) | ✗ | 글상자는 IR `doc-textbox` 슬롯. 도형은 어휘 자체가 없음 |
| 차트 | ✗ | 실질적으로 이미지로 굽는 것 외 방법 없음 |
| 워터마크 | ✗ | hwpx·docx 모두 배경 개체 |
| 댓글 | ⊘ | |
| 스마트 칩(사람·파일·날짜·드롭다운·지도) | ⊘ | 구글 고유. 다른 포맷으로 나갈 때 표현할 대상이 없다 |
| 빌딩 블록 · 문서 탭 | ⊘ | 구글 고유 |

## 범위 밖(⊘)으로 두는 이유

구글 문서 기능의 상당 부분은 **에디터 기능이 아니라 클라우드 기능**이다 — 공유·버전 기록·
댓글·제안 모드·스마트 칩·Gemini. 이것들은 (1) 서버와 계정을 요구하고, (2) hwpx·docx·odt
어느 포맷으로도 나갈 표현이 없다. Narro의 전제는 "클라이언트에서만 파싱한다"이므로
이 축을 쫓으면 제품이 바뀐다. **기준선은 "구글 문서의 편집·서식 기능"으로 좁히는 게 맞다.**

단 두 개는 예외적으로 값어치가 있다: **버전 기록**(로컬 IndexedDB 스냅샷으로 축소 가능)과
**문서 비교**(IR `data-id` diff로 오히려 구글보다 잘할 수 있다).
